# Decisions

Small choices that the code and the [ADRs](adr/) don't settle, with the options considered. Add an entry when you make one. A decision that changes the architecture gets an ADR instead.

## spryte's Shader.set takes arrays and textures, checked against the compiled shader

From spryte 0.13 `Shader.set(name, Float32Array | number[])` sets a `float`, `vec2`, `vec3` or `vec4` array and `Shader.set(name, texture, { smooth })` sets a `sampler2D`. The GL call comes from `getActiveUniform`, read once per compiled program, so the source is never parsed: 4 numbers on a `float[4]` go through `uniform1fv`, and a `Float32Array` on a plain `vec4` through `uniform4fv`. Plain arrays on plain uniforms keep the old `uniform{2,3,4}f` path unchecked, so nothing that worked before starts throwing. Textures take units from 8 up, fixed per program at link time (`uniform1i` once), because units 0 to 7 belong to the batch and a texture's first upload goes through unit 0; the shader's textures are bound before the batch's own units on every flush. Filtering defaults to nearest because textures set on a shader are as often data (lookup tables, pools) as pictures.

Wrong values throw before any state changes: at `set()` while the shader is active, and in `setShader` and `setTarget` for values set earlier. Considered: throwing from the flush (the first version; a throw there escaped from `withShader`'s `finally`, which flushes again, and left the backend on the custom program), parsing `uniform` declarations from the source in `set()` (works on Canvas 2D too, but misses `#define` sizes and duplicates what the driver knows) and copying arrays on `set()` (an allocation per call for a pool that is rewritten every frame; the docs say to call `set()` again after changing one).

## spryte's draw.sprite user values go in their own buffer, used only when set

From spryte 0.16 `draw.sprite(frame, x, y, { user, user2 })` gives a custom shader the same two floats `draw.sprites` gets per copy. The batch instance has no spare float on the sprite path, so the values go in a second per-instance buffer at attribute location 9. A batch uploads it only when a sprite in it set a value; otherwise the attribute stays disabled and reads the constant 0, which spryte resets before each custom-shader draw because other programs on a shared context may set it. Only custom programs read the attribute, and the default program is unchanged. Considered: growing the 52-byte instance to 60 for every draw (15% more upload on every sprite, for a value only custom shaders read), a 60-byte layout only while a custom shader is active (a stride per batch through every writer, for the same result), and routing such sprites through `draw.sprites` with a count of 1 (one draw call each, the cost the issue was about). The no-shader path adds one null check per `draw.sprite`.

## spryte's per-copy shader value is a float through each.user

A custom shader sometimes needs to know which copy of a `draw.sprites` call it is drawing: an index into a row for a staggered effect, a particle's age, a tile variant. From spryte 0.13 `each.user` carries one float per copy on a new instanced attribute, and the shader reads it as `user()`; outside `draw.sprites` it is 0. Considered: packing the value into the low bits of `each.color` (steals colour precision, every shader needs a decode, and it breaks as soon as a tint or alpha multiplies the colour) and a `vec4` per copy (three attributes' worth of upload for a value most shaders never read). The cost is one more vertex attribute on the per-copy program, uploaded when `each.user` is set. That cost on the instanced hot path hasn't been measured: run the `bench/renderer` sprites cases on a GPU machine, with and without `each.user`, before this ships in a release.

## spryte's render tool is deleted: komadori is not spryte's

The entry below deprecated `packages/spryte/tools/render.mjs` and kept it. It is deleted now. The tool became komadori (`debuffjp/komadori`), which is engine-agnostic and has its own repository, package and docs, so a copy of it in spryte's tree is the wrong place for it. The reason for keeping it was that people on old versions still run the command, but `tools/` was never in the npm package (`files` lists `dist`, the README and the licence), so no one on an old version has it, and its only documentation was the cheat sheet, which is not shipped either. The cheat sheet and `golden/README.md` now keep one pointer each to komadori and leave the options and limits to its docs. What stays in this repo that touches komadori: the CI job that uses it, the golden frames for the showcase scenes (they are spryte's record of how its own scenes look), and the demos. Considered: keeping the deprecated copy (it had already drifted by about 800 lines and does less) and moving the golden frames and CI job into komadori's repository (they check spryte's scenes, so they belong beside them). The cost: the repo's rule against deleting what was documented is overridden for this one file, and the old `node packages/spryte/tools/render.mjs` command stops working for anyone who copied it from the cheat sheet.

## The golden-frames job runs komadori from npm, and warp has its own limit

The first version of the golden-frames workflow cloned komadori at a pinned commit because it wasn't on npm. komadori 0.1.0 is on npm now, so the job runs `npx -y komadori@0.1.0` and the clone is gone. The first Linux run also showed what the earlier entry could only guess at: rain passed at the default limit, and warp narrowly failed (0.27 to 0.28% of pixels against 0.25%), mostly the outlines of the title plus a faint speckle over the stars, because Linux rasterises text differently. Warp now runs with `--golden-tolerance 0.5` and blocks again, so it can no longer fail without anyone noticing. Considered: leaving warp report-only (it can fail silently, which is how this was found), taking the title out of the scene (changes a scene for the test's sake), a mask option in komadori (more to build for one title) and regenerating the golden frames on Linux (then they fail on the machines they were made on). The cost: 0.5% is loose enough that a small change to the title alone might pass, and the figure comes from one Linux run. The pin is now a version, which has to be moved by hand.

## spryte's render tool is deprecated in favour of komadori, and kept

(Superseded: the tool was deleted afterwards; see the entry above.)

`packages/spryte/tools/render.mjs` was the first version of the tool that is now komadori (`debuffjp/komadori`). komadori has since gained shader errors with the author's line, golden frames, `--capture canvas` and an MCP server, and the two had drifted by about 800 lines while the cheat sheet still sent agents to the old one. The cheat sheet now points at komadori, and `render.mjs` stays, marked deprecated after 0.12.4 with a note on stderr, because people on old versions still run the command and the repo's rule is not to delete docs for something replaced. Considered: deleting it (breaks the old command and its documentation), keeping both up to date (two copies, one of which has no spryte code in it) and moving komadori into this repo (it is engine-agnostic and isn't spryte's). The cost: a deprecated file in the tree, and the cheat sheet depends on a separate repo that isn't on npm yet.

## The showcase scenes have golden frames in the repo, checked in CI with a pinned komadori

(Superseded in part: the pinned clone and the report-only warp step described here were replaced; see the entry above.)

A change to spryte could shift how the showcase scenes look and nothing would fail: the checks catch a crash, a blank or a frozen scene, not a moved ripple or a different colour. `packages/spryte/golden/` now holds three frames of each of the rain and warp scenes (640 by 360, 321 KB and 761 KB), made with komadori, and `.github/workflows/spryte-golden.yml` renders both scenes on pull requests that touch spryte and compares them. Tolerance came from measurement: on these scenes the same renderer differs by exactly 0, and across a Radeon, an RTX and SwiftShader the worst frame was a mean of 0.153 out of 255 and 0.057% of pixels, so komadori allows 0.01% on the same renderer and 0.25% on another, with a warning. A small real change (the ripple colour) failed on both. Considered: leaving the frames out of the repo and rebuilding them from the base branch in CI (no reference to review, and it compares a branch with itself when both changed), vendoring komadori into this repo (a copy that drifts, and it isn't spryte's), waiting for komadori on npm (the CI step would not exist for a long time) and committing the frames at 1080p (3 to 4 MB a scene). The CI step clones komadori at a pinned commit, which has to be moved by hand. The warp comparison reports without blocking, because its title is drawn with `sans-serif` and a Linux runner has different fonts, and none of this has run on GitHub yet. The cost: about 1 MB of PNGs in the repo, and a person has to approve a new look on purpose.

## browser_not_found says what was tried, and debuff still doesn't download a browser

Papercut #19: on a Linux machine with no Chrome or Edge and a Playwright Chromium that lacked `libnspr4.so`, `debuff scenario` said "No Chromium-based browser found" and repeated the same fix twice, so nothing told you that one browser was installed and failing or where debuff had looked. From 0.31.1 `launchBrowser` builds the message from the launches it already makes: Chrome and Edge with the path Playwright looked in, an installed browser with its own error line, and whether `DEBUFF_BROWSER` is set. When `DEBUFF_BROWSER` fails, the message names the variable and its path and the fix says to correct or unset it. The message keeps paths because it stays on the machine; automatic papercuts still send only "missing" or "launch failed" per browser. Considered: downloading Chromium on first use (a large download no one asked for, and the Linux failure here was a missing system library, which a download doesn't fix), searching more paths such as `/usr/bin/chromium` (a guess per distribution, and `DEBUFF_BROWSER` already covers it) and adding `npx playwright install-deps` to the fix (needs root and only applies to Playwright's own build).
## keiko leaves out test files written for another runner

A debuff game kept 107 `node:test` unit files in `tests/unit/` and ran them with `node --test` before `debuff test`. keiko's discovery took every `*.test.*` under `tests/`, so it loaded those files too, node:test ran all 659 tests a second time inside keiko's process (serially, 369 s against keiko's own 28 s) and one file timed out loading. From keiko 0.8.2, discovery reads each candidate and leaves out files that import `node:test`, `vitest`, `bun:test` or `@jest/globals`; a file named on the command line still runs. Considered: a `.keiko.test.ts` suffix (breaks every existing project), skipping a `tests/unit/` folder by name (a convention, not what the file says) and a config list of ignored paths (another setting, and the default would still double-run). The cost: one small file read per candidate test file.

## keiko picks `--changed` tests by the functions each one ran, in binary coverage

Agents in debuff projects were told to add a test for each mechanic and to keep every fuzz repro, and nothing said to stop: one game reached 659 unit tests and a 7 minute run, re-run after each edit. From keiko 0.9, every run records which functions of the project each test ran (V8 precise coverage through the in-process inspector) and which files its page loaded, and `--changed` runs only tests whose used code or files changed. A change counts when a line-diff of the module as Vite served it, before and after, touches anything outside the functions the test never ran. Considered: the import graph (`vitest --changed` style; useless here, since every test boots `main.ts` and so imports everything), git diffs since a ref (says which files changed, not which tests ran them), block coverage (catches edits in a branch a test skipped, but doubled the platformer template's run time, 4.9 s to 9.2 s) and call-count coverage (correct but 2.2x, since V8 can't optimize counted code). Binary function coverage cost from a few percent to about a third of a run in our measurements, so it's on for every run. Binary coverage reports a function once, and V8 reuses compiled code for identical module source, so keiko appends a boot number to each project module it evaluates; without it, the third test on looked like it never loaded the game. Functions in test files that an earlier test ran count as run by later ones, which only adds tests. Named queues (`--queue push`) keep separate records, so a pre-push hook covers everything since its own last run.

An audit before release found eight changes `--changed` passed while a full run of the same tree failed, each now a case in `tooling/keiko/test/impact.test.ts`: debuff's `/assets/` middleware answered before keiko's recorder saw the request (the recorder now runs first, `enforce: "pre"`); V8 reports an unconstructed class's field initialiser as one range over the class body, hiding static methods that ran (functions that ran are now subtracted from idle spans); `?raw` and `?inline` modules have no source map, so V8 doesn't know their id (the evaluator lists every module it ran, and one without coverage counts as used in full); the disk-hash shortcut missed output that depends on other files (`.env` files, files the Vite config imports and the tsconfig `extends` chain now count as setup, and modules using `import.meta.glob` are always re-transformed); linked packages outside the root weren't tracked; and test-side modules carried state between tests. For that last one, selection is per file, not per test: any change to a module that outlives one test makes every test that loaded it due, and a due file runs whole. Considered: guessing from a test file's source whether its tests share state (top-level `let`, mutated objects, local imports), which is fragile in the direction that skips tests. Datadog's JavaScript test impact analysis and Vitest's `--changed` also select whole files. The cost: a suite kept in one file reruns all its tests whenever one is due, so the guidance asks for one file per mechanic. A second review found five more: a filtered run advanced the queue's setup hash for tests it left out (the hash is now kept per test); a syntax error inside a function that never ran passed the span check, and so did an edit that closes such a function and adds top-level code (changed code must now compile, and each edit's brackets must stay inside it, or the module counts as used); a plugin's virtual module built from a file wasn't tracked; files a test read with `node:fs` weren't inputs; and a tsconfig with `"@/*"` and `"src/**/*"` broke the comment stripper. Still not seen: state that tests in different files pass through a shared helper.

## scale: "pixel" scales by a fraction below one device pixel per unit

Papercut #25: with `scale: "pixel"`, `pixelSize: 1` and a 1280 by 720 minimum, a 1024 wide window showed a 1280 wide canvas, because `Game.resize` never went below one device pixel per unit. The JSDoc already said a container too small for the minimum scales down. From 0.29.3, when even one device pixel per unit doesn't fit, it keeps the fractional `fit` scale, still grows the logical size along the spare axis and keeps the minimum. Pixels aren't crisp in that case, which is the same trade `fit` makes. Considered: letterboxing at one device pixel with a CSS downscale (the same blur, plus bars and a logical size that no longer follows the container), keeping the overflow with a dev warning (leaves games cut off for players, against what the docs said) and lowering the logical minimum (changes the game's layout, which is the creator's call). Containers that fit at one device pixel or more scale by whole device pixels as before.

## The spryte mirror gets a copy on each release, not a subtree split

`debuffjp/spryte` stopped at 0.7.3 while npm reached 0.12.1, because the `git subtree split` from ADR 0013 was a manual step. The mirror also has its own files (issue templates, dependabot, its standalone CI, brand images, charts and a lockfile) that a split doesn't contain. `scripts/sync-spryte-mirror.mjs` runs from the Release workflow and commits a copy of the package on top of the mirror's history when the versions differ, leaving those files alone and regenerating the lockfile. Considered: force-pushing the split (deletes the mirror's files and rewrites public history) and merging the split (keeps per-commit history on the mirror but conflicts wherever the mirror diverged). The cost is one mirror commit per release: per-commit history stays in this repo, and each sync message names the debuff commit. Outside contributors' commits are replayed ahead of that commit, because GitHub's contributor list goes by commit author.

## spryte warns about sprites across images only in development

Papercut #37: `draw.sprites` with `each.frame` frames on more than one image drew one quad per copy, and only the JSDoc said so. From 0.12.3 spryte warns once per renderer when `import.meta.env.DEV` is true, using the guard `@debuffjp/core` uses, so production builds drop the check. Considered: an unconditional warning like the detached-array one (that one means nothing drew, but mixing images is a legitimate choice a shipped game would then log for every player) and throwing (breaks games that accept the cost). The cost: spryte used outside a bundler that sets `import.meta.env` never warns.

## The asset build warns about images over 4096 pixels on a side

Papercut #30: a 19800×80 grid sheet drew every frame as a black rectangle, and neither the build nor the console said why. From 0.29.3 `compileAssets` reads each PNG's header and warns when either side is over 4096 pixels. Considered: 2048 (the only size WebGL2 promises, and the atlas default, but it would warn about 4096 backgrounds that work on every WebGL2 device in practice), 8192 and 16384 (common on desktop GPUs but missing on some phones, so a game could pass the build and draw black there) and a config option for the limit (more surface than a warning needs; nothing reads it yet). 4096 is the largest size that works everywhere in practice, so a warning means a real risk. The check covers PNGs only, since that header gives the size without decoding; JPEG and WebP would need a parser each. spryte doesn't check `MAX_TEXTURE_SIZE` when it uploads an image yet: that would add bytes to every game and is a separate change.

## Build reports spend maximum Brotli effort on code and HTML

Papercut #21 reproduced with 40 binary files of 8 MiB each: `debuff build --json` took 234.48 s on macOS arm64 with Node 26.7.0. `buildReport` compressed every file at Node's default Brotli quality 11. From 0.29.1 it uses quality 4 for assets, source maps and other files, keeping quality 11 for code and HTML so existing code budgets stay comparable. Raw bytes, gzip settings and shipped files stay the same. Considered: lowering quality for every file (changes code budgets), skipping compressed asset sizes (changes the report's contract) and caching reports (adds cache invalidation and still leaves the first build slow).

## mossfell's long flash checks get a local 120 s step budget

The accessibility scenario captures 300 frames in one flash check. Two fresh Linux CI runs hit the default 60 s step limit (papercut #42), so this scenario sets `stepTimeout: 120`. The frame counts and flash assertions stay the same. Considered: splitting each check (could miss flashes across the boundary), raising the default for every project (delays real hang detection elsewhere) and setting a budget on this one scenario.

## agent-cli is a repo script, not npm scripts or an MCP tool

`bin/agent-cli` (logic in `scripts/agent-cli.mjs`) gathers the lookups and commands that 98 past agent sessions in this repo repeated: status, check with only the failures, one-file tests, exports, docs search, versions, release, site, papercuts and ports. Options considered: more `npm run` scripts (no `--json`, no arguments without `--`, and npm's banner on every call), tools on the debuff MCP server (that server is for people making games, not for working on debuff) and a script with no dependencies. The script won: one entry point with `--help` and `--json`, nothing to install, and it runs where the agent already has a shell.

## smoothMotion reads a function of objects, and frozen frames render at alpha 1

`smoothMotion(game, () => [player, enemies, shots])` saves positions in a `WeakMap` on every `beforeUpdate`, for whatever the function returns then. overbuffed, the evidence for roadmap item 2, kept `prevX`/`prevY` (or `px`/`py`) on every object and copied them at the top of each step. Considered: `track(o)` / `untrack(o)` per object (games spawn and drop shots every step and would forget to untrack, so it leaks), and fields written onto the objects (changes their shape and their `inspect()` output). A saved position is only used if it came from the step that just ran, so new objects, frozen steps and `snap()` all draw where the object is.

While writing it, a probe showed the camera's view jumping by up to 7 px on every frame of `game.freeze()`: no steps run, but `renderAlpha` kept changing. `Game.render` now passes alpha 1 while frozen, to the camera, the scene and the render hooks. Considered: holding only the camera (`camera.hold()` on frozen steps; it still blended until the first frozen step ran, and games' own lerps kept wobbling). Scenario captures render at alpha 0 between whole steps, so one taken during a freeze now shows the camera one step further on.

## Dev clips save through the dev server, and sharing stays out of games

The dev panel's **clip** button and the `saveClip` hook post the video to `/__debuff/capture`, which writes `.debuff/captures/`. Returning it through the agent link instead would push several MB through one SSE message and a 10 s RPC timeout, and the human's button would have nowhere to save but Downloads. `.debuff/` is already in new projects' `.gitignore`, so clips don't land in git; `debuff ship press` copies them into the kit. Clips prefer MP4 because X and most stores don't take WebM.

`@debuffjp/dev` now depends on `@debuffjp/share` for `ClipRecorder` rather than keeping a second copy of the staggered-recorder logic.

Templates don't get share buttons, hashtags or "made with" tags. What a game shows is the creator's call; the tooling helps on the developer side (captures, press kits, drafting posts) and `postIntent` is there for anyone who wants it. Considered: a share button on template game-over screens (rejected by the maintainer as too much control over what people make).

## keiko touch pointerIds start at 2

A finger's DOM `pointerId` in keiko is its touch id + 2 (`TOUCH_POINTER_OFFSET` in `tooling/keiko/src/driver.ts`). `Touch.identifier` keeps the id the scenario gave. Before this, finger 1 and the mouse both had `pointerId` 1, so a game that tracked pointers by id mixed them up. Considered: a separate id range per kind (larger change to scenario files), and rejecting touch id 1 (breaks existing scenarios).

## Commit messages and docs omit the serial comma

The repo writes "a, b and c". When `scripts/lint-prose.mjs` was added, 22 lists used a serial comma and about 340 didn't, so the lint doesn't require one.

## Papercut reporting stays out of the browser packages and keiko

myaku and spryte don't report papercuts themselves, though the board has a section for each. They run inside players' browsers, and a game must never send anything to us on its own. Their friction reaches the board through the debuff CLI and MCP server, which already run when a developer works on them, and through agents calling `report_papercut`. Considered: a dev-only reporter in `@debuffjp/dev` (still runs in the developer's browser, and would need its own disclosure) and doing nothing (the sections stay empty). keiko stays out too (maintainer's call, 2026-10-30): it is a standalone tool that Phaser and Pixi users run without debuff, and they never agreed to report to the debuff board.

From 0.24.2 `debuff dev` reports bugs the dev tools catch inside debuff, and this still holds: `@debuffjp/dev` only fires a `debuff:bug` event in the page, the dev server (the CLI, in Node) checks the signature and sends it, and nothing in the page talks to the board. A built game has no `@debuffjp/dev` and sends nothing. The papercuts notice was versioned so the new reports were disclosed before any went out (maintainer's call to make it opt-out for everyone, 2026-10-31).

## Biome's Markdown formatter stays off

Biome 2.6 formats Markdown by default, which would reformat every README, ADR and changeset in one commit. The bump to 2.6.3 turns it off in `biome.json`, so the upgrade changes no files. The new lint rules it brings (`useMathMinMax`, `useDateNow`) stay warnings: rewriting core's `clamp` as `Math.min(Math.max(...))` changes what it returns for NaN. Considered: accepting the reformat (a large diff nobody reviewed for meaning), and staying on 2.5 (dependabot keeps reopening the bump).

## keiko mutate: what a param mutant tries, and where results go

A number param goes to each end of its declared range, or to 0 and double its value when it has none; a boolean flips. debuff rejects values outside a param's range (`ParamGroup.set` throws), so the out-of-range values first planned (x0, x2, a flipped sign) would have been unviable for every debuff game. The range ends are values a designer could ship, so a missed one means no test depends on the param anywhere in its range. Considered: halving and doubling clamped to the range (more mutants, and the halves mostly duplicate what the ends show).

Seed and frame-rate mutants are reported as unviable for debuff games rather than left out, so nothing is skipped without a line saying why. The seed offset is 7919, the same one `test.deterministic` uses for its second run.

Results go to `mutants.out/`, the folder cargo-mutants and mutant.cafe use, so agents that know either tool know where to look. Considered: `.debuff/mutants` (keiko runs outside debuff projects too) and `.keiko/` (a new hidden folder for one command). The command is `keiko mutate`, a subcommand like `keiko init`, rather than a `henka` binary: henka has no runner of its own.

Changed in henka 0.1.0 (before its first release): henka gained its own `henka` command for Vitest projects, since source mutants need a runner and Vitest is the one Vite projects already have. `keiko mutate` stays a keiko subcommand.

## Replay checkpoints hash each part of the state and only warn

From 0.31 a recording keeps a checkpoint every 60 ticks, so a replay can say where it stopped matching (the idea comes from rollback engines such as bones, which compare state checksums to find desyncs). Each checkpoint is an 8-digit FNV-1a hash per part: `scene`, `events`, each top-level key of `inspect()` and each plugin snapshot. Considered: one hash per checkpoint (25 bytes, but a drift only names the tick) and the full state per checkpoint (names the exact path, but a few minutes of play could make a replay megabytes). Per-part hashes cost a few hundred bytes a second and name the area, such as `state.enemies`.

A drift is a warning, not a failure. Replays get saved as regression scenarios, and every later change to the game would fail them on checkpoints even when the captures and `expect` steps still pass. Considered: failing (brittle in exactly that way) and rewriting checkpoints with `--update` (edits the user's scenario file, where `--update` only ever writes baselines). The camera is left out of the hash because its size follows the window, which differs between the human's tab and a scenario's viewport.

## henka source mutants: a warm Vitest per job, a Vite plugin, test files from the baseline

Each job keeps a Vitest process open whose only change is a Vite plugin that returns the mutated text for one file; between mutants it invalidates that file in every project's module graph and in the workers. The baseline turns on Vitest 5's `experimental.importDurations` with no limit, which lists every module each test file ran, so a mutant run goes straight to the test files that loaded its file instead of working out Vitest's `related` graph again. Considered:

- Stryker's schemata, every mutant compiled into the code at once behind a switch. No re-transform per mutant, but the instrumented code has to type-check and survive every other plugin's transform, and a mutant in code that runs at import needs a full reload (Stryker's "static" mutants).
- cargo-mutants' way, patching a copy of the project on disk. Needs a copy per job (the debuff repo is gigabytes with `node_modules`) and a watcher could pick up a half-written file.
- A fresh Vitest process per mutant, the first version. Simplest, but starting Vitest was most of each run.

A run past the timeout has its process tree killed (taskkill on Windows, a process group elsewhere), counts as caught, and the job starts a new process. `fsModuleCache` is off in mutant runs so a mutated transform never lands in Vitest 5's disk cache. A file that another `enforce: "pre"` plugin changed before henka's plugin runs is reported as unviable rather than mutated blind.

The operators are the smallest set that finds the gaps a game's tests leave: arithmetic, comparison boundaries, logic, sign, number literals and function bodies. Left out for now: string literals (mostly log and error text), array and object literals, optional chaining and regular expressions, which Stryker has.

## Scenario steps go to the page in batches of up to ten seconds

`debuff scenario` made one `page.evaluate` round trip per step, about 2.7 ms each. A recorded replay has a step on nearly every tick (a pointer move and a wait), so five minutes of mouse play was 36,599 round trips and 90 to 106 s, against 3 to 4 s for a plain five-minute `wait`. From 0.31 the runner turns each run of input, `wait` and `checkpoint` steps into dev hook calls and makes them in one call (`callHooks`), which brought that replay to 2.7 to 2.9 s. Steps that need the runner (`expect`, `until`, captures, accessibility and plugin steps) still go one at a time. A batch covers at most 600 ticks and 2,000 calls, so the per-step `stepTimeout` still catches a hung game. Considered: playing the whole replay in the page in one call (a hang would only show after the full timeout, and the report couldn't say where it hung) and moving step translation into the page (duplicates `runStep`, which Node tests cover).

## launch.playerCard is one optional object, and a bad one fails the build

Papercut #39: `debuff build` always wrote `twitter:card` `summary` or `summary_large_image`, so a game that wanted to play inside an X post rewrote the tags after the build. From 0.32 `launch.playerCard: { site, width, height, url? }` switches the card to `player`; leaving it out keeps the old card. The object's presence is the switch, since a player card can't be written without the account and the iframe size. Considered: `launch.card: "summary" | "summary_large_image" | "player"` with the player fields beside it (a second key that only means something with the first, and picking the summary card by hand isn't something anyone has asked for) and a free-form `launch.meta` map of extra tags (the same post-build rewrite in a different place, with nothing checked). The player defaults to `launch.url`, the game's own page; `playerCard.url` is there for hosts whose public page isn't the one that can be framed. `twitter:player:stream` is left out: it is for audio and video streams, and a hand-written tag in `index.html` still wins for anyone who needs it.

A config X can't use throws `config_invalid` (exit 2) instead of warning, because a broken player card fails quietly on X: the post shows a plain link or nothing. Checked: `site` matches `@` plus 1 to 15 letters, digits or underscores; `width` and `height` are whole numbers above 0; `launch.url` is set (`twitter:image` needs an absolute address); the player address is https; there is a preview image. The check runs after Vite bundles, where the other launch files are written, and before anything is written to `dist/`. Not checked, because it needs X: whether the domain is allowed to show player cards, the image's pixel size and whether the player page allows framing.
## dev_hooks_missing names a cause from what the page and src/ show

When a scenario's page doesn't have its dev hooks ready in 15 s, `debuff scenario` reads the page once more (is `window.__DEBUFF_DEV__` set, is `?debuff-scenario` still in the URL) and looks for `@debuffjp/dev` in the project's `src/`. The message then names one cause, in this order: hooks set but the URL lost the query (the dev tools started in live mode), nothing in `src/` imports `@debuffjp/dev`, a failed request or console error while loading (the first is quoted), or the game waits for something before installing the dev tools. A production build isn't a cause here: scenarios always run the Vite dev server. Considered: one message listing every cause (the reporter's case, papercut #23, got the same "add devTools" fix whether or not the game had it) and watching which modules the page loaded to tell whether `@debuffjp/dev` ran (module URLs differ between a linked workspace, prebundled deps and other bundlers). The `src/` check is a text search: a game that imports the package only from outside `src/` is told nothing in `src/` imports it, and one without a `src/` folder gets a message naming both of those causes.
## spryte's custom shaders stay off vector shapes; the docs say so

Papercut #26: a full-screen vignette drawn as a rect inside `withShader` seemed to do nothing, and the docs said "shapes get (0, 0)" from `frameUv()`, so the reporter drew a 2 by 2 render target and scaled it over the screen instead. On a real GPU, `rect()`, `line()` and `circle()` run the effect with `uv` and `frameUv()` both going from (0, 0) to (1, 1) across them, and a vignette on a `rect()` works. The vector shapes (`polygon`, `polyline`, `roundRect`, `ring`) and `mesh` never run the effect: their batch uses the built-in fragment stage, as the 0.3.0 changelog said. From 0.12.4 the JSDoc and `docs/api.md` say that, with a vignette on a `rect()` as the example, and browser checks pin it. Considered: compiling each custom effect against the shape program as well, so vector shapes take it with `frameUv()` at (0, 0) (a second program per shader, a behaviour change for games that draw shapes inside `withShader` today and no use case in the report) and leaving the docs and adding only the example (keeps the wrong sentence).
## An audio stream's stop() is final

From 0.31.1 `audio.stream()` tracks one state (playing, paused or stopped) instead of a `wanted` flag. `stop()` unloads the element, so `resume()` after it does nothing; call `stream()` again to play the track afresh. Before, `resume()` during a `stop(fade)` restarted playback that the pending unload then cut off, and after the unload it armed a retry that could never succeed. Considered: letting `resume()` cancel a pending fade-out (needs the gain restored and the unload timer cancelled, and gives stop two meanings). A blocked `play()` now waits for the context unlocking or the next pointer or key gesture, with one wait armed at most: media elements have their own autoplay rules, so the context can already be running while the element is still blocked.

## spryte rebinds all 8 sprite units when drawing into a target

#118: a target refilled with `draw.into()` every frame and also drawn every frame stayed blank, with a feedback-loop error per draw. The earlier draw left the target's texture bound to a texture unit, and every spryte program samples all 8 sprite units, so the next draw into the target read the texture it wrote. From 0.16 `setTarget` binds the white texture to all 8 units after binding a target's framebuffer, and the linear-light framebuffer's texture no longer stays on unit 0 after it is created or presented. Considered: the issue's proposal, rebinding only the units that `units` records as holding the target. `units` records what sprite batches bound, but uploads, `copy()`, `copies()`, static layers and a target's creation bind units without recording it, and those can run mid-batch, where updating the record would break the pending batch. A full mirror of every unit's binding would touch all of those paths. Rebinding all 8 costs 16 GL calls per `into()`, none on the per-sprite path.

## Compressed textures: one Basis encode at build time, transcoded to each GPU format

#120: `assets.compress` writes BC7, ASTC 4x4 and ETC2 copies of every PNG as plain KTX2 files, and the runtime loads the one the GPU decodes. The CLI encodes each image once to UASTC with Basis Universal, then transcodes that to the three formats, so every variant comes from the same encode and quality matches across GPUs. Basis comes from `ktx2-encoder` 0.6.0 (MIT, the Basis WASM is Apache-2.0, 3.4 MB installed), pinned exactly because its own exports only cover its encoder: debuff loads the bundled module, encoder and transcoder, by path from `tooling/cli/src/assets/ktx2.ts`, the only file that touches it. Considered: `gpu-tex-enc`'s per-format native encoders (18 MB for ASTC alone, last published 2024, one maintainer), shelling out to `toktx`/`basisu`/`astcenc` (an install step for every user, and `ktx create` can't write BC7 blocks), and shipping Basis files with a transcoder in the game (a few hundred kB of WASM at runtime, against the rule of fewer runtime dependencies). The game side needs no new code beyond spryte's KTX2 reader. Measured on a 960x540 template image: 244 ms to encode with 10 mip levels, 2 to 9 ms per transcode, 693 kB per variant against 2.07 MB as RGBA. Results are cached by content hash in `.debuff/cache/ktx2`.
